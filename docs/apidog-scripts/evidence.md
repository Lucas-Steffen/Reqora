# Apidog pre/post-processor scripts: static evidence

Investigation date: 2026-10-16. Scope: how Apidog 2.8.50 runs **pre-processors** and **post-processors** (custom scripts, assertions, variable extraction, database operations, waits), what the `pm` script API contains, and how results reach the UI. The work supports a clean-room reimplementation in Reqora. No Reqora source code is part of this document.

Method: literal string search over the packaged members only. No Apidog code was executed, required or evaluated. To regenerate the raw ledger (gitignored), run:

```sh
node docs/apidog-scripts/tools/scan-scripts.cjs
```

Outputs: `evidence/raw/script-facts.json` (each fact with offset, enclosing module id, a short excerpt and ±500-character context), `evidence/raw/sandbox-require-modules.json`, `evidence/raw/script-term-counts.json`, `evidence/raw/unpacked-members.json`, and `evidence/extracted/facts-table.md`.

## Inferences

Each inference cites the facts it relies on. None of them was confirmed at runtime.

- **I1. Sandbox technology.** Scripts run through the Postman stack: `@tarslib/runtime` → `@tarslib/sandbox` → `@tarslib/uvm` → `uniscope`. Inside the Electron desktop runner, uvm uses its **in-process `node:vm` bridge**, not the worker bridge. `getSandboxContext()` supplies `apiExtend` as a function, and uvm picks the vm bridge exactly in that case (S04, S06, S09, S11, S12). The `worker_threads` bridge exists but is a fallback (S10). The boot code removes non-allowlisted globals ("purse"), and each script runs in a `uniscope` scope (S21, S22). `node:vm` is not a security boundary. The real host `require` is visible to the boot code (S06, `require:eval("require")`) before the boot code nulls it.
- **I2. Where it runs.** The processor-to-event compiler and the sandbox setup sit in the runner bundles (`worker.groupRunner.js` / `worker.utilityRunner.js`; the bytecode `worker.runner.jsc` contains the same identifiers). These communicate through `process.parentPort`, which exists in Electron `utilityProcess` children (S26, U06). Scripts therefore run in a utility process spawned by main, **not in the renderer and not in the main process**. A second copy of the sandbox in renderer chunk 41230 (S27) probably serves the web build; it was not traced.
- **I3. Timeouts.** The sandbox execution timeout is `min(timeout.script, timeout.global)` (S18). The Apidog runner sets only `timeout.global` (S19). The effective script timeout therefore equals the run's global timeout: **5 min** (`a8=5`) for runs whose id is `"temp"` (S20), otherwise `max(1440 min, request timeout)`, or 59,940,000 ms if the request timeout is 0. When it fires, the error text is `sandbox: synchronous|asynchronous script execution timeout` (S17). Separately, every bridge dispatch, including the synchronous part of an `execute`, is a `vm.runInContext` call bounded by uvm's default `bootTimeout` of **300,000 ms** (S05, S07, S08). This is what can interrupt a busy loop. The asynchronous timer cannot. Unconfirmed: `"temp"` presumably identifies ad-hoc endpoint sends (Send button / debug mode).
- **I4. Confirmed API surface.** Runtime facts, not only typings:
  - `pm.environment`, `pm.globals`, `pm.collectionVariables`, `pm.moduleVariables` (the same object as `collectionVariables`), `pm.variables`, `pm.iterationData`, `pm.teamGlobals` (P02).
  - Variable-scope methods: `get`, `set`, `unset`, `has`, `clear`, `replaceIn`, `toObject` (P16). Additionally `pm.variables.replaceInAsync`, an async host function (P08).
  - `pm.globals.*(…, "TEAM" | "PROJECT")` scope switching (P09).
  - `pm.variables` lookup order: local → iterationData → environment → collection/module → globals → teamGlobals (P03).
  - `pm.request` and `pm.response` are postman-collection `Request`/`Response` subclasses (P17, P18, P19). Request: `url`, `method`, `headers`, `body`, `addHeader`, `upsertHeader`, `removeHeader`, `addQueryParams`, `removeQueryParams`, `getBaseUrl`. Response: `code`, `status`, `headers`, `responseTime`, `text()`, `json()`, `size()`.
  - Apidog additions on the response: `setBody`, `setData`, `originalText`, `originalJson` (P06). `pm.response.to` and `pm.request.to` assertions come from chai + chai-postman (P07, P10).
  - `pm.test(name, fn[, done])`, `pm.test.skip`, `pm.test.index` (P12). `pm.expect` is chai `expect` (P10). Apidog adds `pm.expectWithKey` (P10, C04).
  - `pm.sendRequest(urlOrRequest, cb(err, res, history))` is callback-only and has no Promise return (P04).
  - `pm.cookies` is a CookieList, and `pm.cookies.jar()` returns a jar with `get`, `getAll`, `set`, `unset`, `clear` (P15, C01).
  - `pm.info.{eventName, iteration, iterationCount, requestName, requestId}` (P01). `pm.visualizer.set/clear` (P05). `pm.vault.get` (P08).
  - Extension functions mounted through `apiExtend`: `pm.dataSource`, `pm.execute`, `pm.executeAsync`, `pm.__json5Parse`, `pm.liveRequire` (S12, P11).
  - `console.log/info/warn/error/debug/clear` (P13). Globals available to scripts: `Buffer`, `setTimeout`/`setInterval`/`setImmediate` and their `clear*` functions (S14). `$$` is an alias of `pm` (S11, S15).
  - Legacy Postman v1 globals: `tests`, `globals`, `environment`, `data`, `request`, `responseBody`, `responseTime`, `iteration`, `postman.*`, `_`, `CryptoJS`, `tv4`, `xml2Json`, `Backbone`, `cheerio`, `atob`, `btoa`. They are present unless the script starts with `"use sandbox2"` (S16, S24, P14).
- **I5. Typings vs runtime.** The editor typings declare `pm.execution` (`skipRequest`/`setNextRequest`/`location`) and `pm.require` (T03). The pm constructor does not assign them, so they are **not confirmed** to work. The typings hide `pm.collectionVariables` behind a comment and advertise `pm.moduleVariables` instead (T02), although both exist at runtime (P02). There is no `apidog.*` object. The only alias is `$$` (S11, S15).
- **I6. Execution order.** For an endpoint run, the processor list is ordered as follows (O06, O07, O08, O11, O17).
  - Pre: `[test-scenario pre-processors] → root (module root folder, else project "common" processors) → folders from outermost to innermost → (for a test case: the endpoint) → the item's own enabled processors`.
  - Post uses the **same top-down order** and is not reversed: `[test-scenario post] → inherited root→folders(→endpoint) → own enabled → metaInfo post-processors`.
  - Within that order, each pre-processor is assigned to one of two phases by its position relative to the built-in **Variable Substitution** placeholder. Items before it run as `prerequest`, before `{{var}}` resolution. Items after it run as `presend`, after resolution and just before sending (O12, O13, O14, O15, L10).
  - Post-processors all run as `test` events (O04).
  - Helper scripts for assertion and extractor processors are prepended as the first `prerequest` events (O05).
  - Request edits to `url`, `method`, `headers` and `body` are copied back onto the outgoing request after both pre phases (O18, O19).
- **I7. Inheritance controls.** There is no single "inherit parent scripts" switch. Each processor defined on a parent has `defaultEnable`, shown as "ON in children" (L09). Each descendant stores an `inheritPreProcessors`/`inheritPostProcessors` map keyed by processor id with `{enable, defaultEnable}` overrides. Overrides apply top-down, and the current item's map has the final say (O09, O10). The UI shows "Inherited from Folder/endpoint" and offers "Move to Parents" (L08, L12). Test cases can carry `inheritPre/PostProcessorsSnapshot` instead of live inheritance (same `getProcessors` in module 657914 as O06/O17; see the raw context).
- **I8. Processor types.** The event builder handles `customScript`, `commonScript` (a project "Library Script" referenced by id), `assertion`, `extractor` ("Store Variable"), `httpApiExtractor`, `database`, and `delay` ("Wait"), plus the `placeholder` divider (O01, O02, O03, L11). Assertions, extractions and DB operations are compiled into generated `pm` scripts. They are not interpreted natively (C01–C05). `delay` is a script that keeps a timer alive (O02). An optional YAPI-compat prelude exists for custom post-scripts (O16).
- **I9. Surfacing results.**
  - Console calls become `{cursor, level, logs}` events (U01, P13). The renderer formats them and recognises processor in/out and external-script label markers (U04).
  - `pm.test` records `{name, async, skipped, passed, error, index}` (P12). The runner turns them into `assertion` events with `{name: "AssertionError", message, expected, actual, stack}` on failure (U02).
  - Uncaught errors become `step` errors (U03).
  - UI strings: "Console", "Assertion Results", "PreProcessor Error: ", "PostProcessor Script Error: ", "Library Script PreProcessor {name} Error: " (L01–L05).

## Implications for Reqora

These are recommendations for a clean-room design. They are not Apidog behaviour claims.

1. **API subset to expose (MVP).**
   - Variables: `pm.environment`, `pm.globals`, `pm.collectionVariables`, `pm.variables`, `pm.iterationData`, each with `get/set/unset/has/clear/replaceIn/toObject`. Provide `moduleVariables` only if Reqora adopts modules.
   - `pm.request`: `url` (string and query helpers), `method`, `headers` (`get/add/upsert/remove`), `body` (`raw`/`mode`). Edits must apply to the outgoing request.
   - `pm.response`: `code`, `status`, `headers.get`, `responseTime`, `responseSize`, `text()`, `json()`, plus `setBody()`.
   - Tests: `pm.test` (+ `skip`), `pm.expect` (chai-4 BDD subset), `pm.response.to.have.status/header/body/jsonBody`.
   - `pm.sendRequest` with a callback. A Promise return would be a Reqora extension and should be labelled as such.
   - Also: `pm.info`, `console.{log,info,warn,error,debug,clear}`.
   - Defer: `pm.cookies.jar`, `pm.visualizer`, `pm.vault`, team globals, legacy v1 globals, `$$`, and all `apiExtend` functions (database, external programs, live npm).
2. **`require()` allow-list.** Start with a small, audited set: `crypto-js`, `lodash`, `moment` or `dayjs`, `uuid`, `ajv`, `xml2js`, `jsonpath-plus`, `atob`, `btoa`, `chai`, `assert`, `buffer`, `url`, `querystring`, `csv-parse`. Do not expose `fs`, `os` or a live npm loader.
3. **Isolation.** Run scripts outside main and renderer, in a utility process or worker, as Apidog does with its utility process (I2). Do not rely on `node:vm` as a security boundary (I1). Prefer a fresh context per execution, no host `require`, and an explicit bridge for `sendRequest` and variable writes.
4. **Timeouts.** Enforce a hard limit that also interrupts synchronous loops, for example a vm `timeout` plus a wall-clock kill of the worker. Apidog's effective defaults are 5 min for ad-hoc sends and 300 s per synchronous dispatch (I3). Reqora should make the limit configurable, with a shorter default such as 30 s.
5. **Ordering model.** Use root → folders (outermost first) → endpoint → own, for both pre and post. Give each processor `enabled` plus `enabledInChildren` (`defaultEnable`), and let each descendant override them by processor id. Keep a "Variable Substitution" divider so that a pre-processor runs either before (`prerequest`) or after (`presend`) template resolution (I6, I7).
6. **Processor types (MVP).** Support custom script, assertion, extract variable and wait. Compiling assertions and extractions to the same script runtime keeps one execution path, as Apidog does (I8). Database operations, library scripts and external programs can come later.
7. **Result model.** Use `TestResult {name, passed, skipped, error?: {name, message, expected?, actual?}, index}`, `ConsoleEntry {level, args (serialized), source: pre|post|processorId}`, and a script error tied to the processor id. Show "Console" and "Test Results" panels (I9).

## Limits

- Static analysis only. No script was run in Apidog, so ordering, timeouts and API availability are read from code, not observed.
- The `.jsc` bytecode was not decompiled. The traced logic comes from the plain-JS `worker.groupRunner.js`. That the bytecode `worker.runner.jsc` (likely the runner for single sends) uses the same processor builder is inferred from shared identifier strings (`calcProcessors`, `getSandboxContext`, `customScript`, `timings.preProcessorsStarted`), not proven.
- The meaning of run id `"temp"` (5-min timeout) is inferred.
- The method lists for `Request`, `Response` and `VariableScope` come from `node_modules/@tarslib/collection`. The copy bundled inside the sandbox boot code (`@tarslib/sdk` / browserify module 312) was not enumerated method by method.
- The `require()` list is the bundler configuration. Versions and actual inclusion of each module in the boot code were not verified, and the behaviour of `fs`/`os` inside the boot code is unknown.
- Only the en-US locale was read. Renderer chunk 41230 (second sandbox copy) and the Advanced Mock sandbox were not traced.
- The inventory lists native modules (ibm_db, kerberos, oracledb) as unpacked, but they are absent on disk. They are unrelated to script sandboxing.
- Excerpts are kept short on purpose. Fuller context for each fact is in the gitignored `evidence/raw/script-facts.json`.
